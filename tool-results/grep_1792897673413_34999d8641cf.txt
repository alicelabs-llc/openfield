27:## 1. Protocolo de arranque de sesión (BOOT — ejecutar SIEMPRE primero)
29:1. **Memoria entre resets**: verificar `/home/z/my-project/worklog.md` Y `/tmp/my-project/` (sobrevive resets — Task 99). Si `/home` volvió a snapshot viejo, `/tmp/my-project` tiene el estado vivo.
30:2. **Lectura interrogativa del worklog** *(v3.0 — context engineering, no re-ingesta total)*: últimas 3 entradas íntegras + `grep -i` temático según la tarea del usuario. Prohibido re-ingerir el worklog completo si es grande (presupuesto de atención, regla 22). Si el usuario pide historia completa: leer por secciones bajo demanda.
31:3. **Memoria alethech** *(v3.2 — fail-closed)*: `alethech verify` PRIMERO (cualquier commit inválido = cadena comprometida → INCIDENTE: operar solo desde worklog + `estado_sitio.json`, reportar, jamás sobrescribir para "arreglarla") → continuidad de checkpoint (el checkpoint HEAD debe ser ancestro del HEAD actual; si no = ROLLBACK detectado) → `recall --last 5` (`alethech_recall.py` maneja el bug conocido `:`/`%3A`). Sin store ni CLI instalado (`pip install alethech`): declararlo y operar desde worklog. La cadena Ed25519 es la fuente de verdad de estado entre sesiones.
33:5. **Health checks + snapshot de drift**: `/api/health` (200), `/api/skills.json` (200), `/uta/conformance/vectors/_index.json` (schema vivo) → guardar en `estado_sitio.json` y COMPARAR contra el snapshot previo (drift programático). Sitio caído → **incidente primero** → cargar skill `runbook-incidentes`.
