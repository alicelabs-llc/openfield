Summary

Severity: Medium ($150 USDC — Stage 1 Public Beta Bug Bounty)
Affected In-Scope Modules:

  • src/privacy/commitment.rs (CommitmentGenerator::commit_note, CommitmentGenerator::verify_opening, CommitmentGenerator::commit)
  • src/privacy/proof_codec.rs (field_to_bytes, bytes_to_field, deserialize_proof, deserialize_vk)
  • src/privacy/transaction.rs (TransferTx::verify_structure, WithdrawTx::verify, TrackedTransaction::mark_verified, TrackedTransaction::mark_rejected)
  • src/coordinator/mod.rs, src/coordinator/role.rs, src/node/mod.rs, src/validator/mod.rs (try_promote_if_stalled, start_stall_watchdog, start_heartbeat_broadcast, submit_task)

We identified four distinct zero-duplicate vulnerabilities across src/privacy/ (commitment.rs, proof_codec.rs, transaction.rs) and the src/node/ + src/coordinator/ HA failover and shard-dispatch state machine:

Vulnerability 1: CommitmentGenerator::commit_note Uses Poseidon While CommitmentGenerator::verify_opening / commit Use BN254 Pedersen, Causing 100% Verification Failure (src/privacy/commitment.rs:10–29)

Root Cause

In src/privacy/commitment.rs:10–29, CommitmentGenerator mixes two incompatible cryptographic commitment schemes on the same struct:

  1. CommitmentGenerator::commit(value: u64, randomness: &[u8; 32]) -> Commitment (lines 14–17) and CommitmentGenerator::verify_opening(commitment: &Commitment, value: u64, randomness: &[u8; 32]) -> bool (lines 26–28) delegate to crate::privacy::pedersen::commit and crate::privacy::pedersen::verify, which compute and verify a compressed BN254 G1Affine elliptic-curve Pedersen point $C = v \cdot G + r \cdot H$.
  2. However, CommitmentGenerator::commit_note(note: &ShieldedNote) -> Commitment (lines 21–23) delegates to note.commitment() (src/privacy/types.rs:255–262), which computes a 4-input Poseidon sponge hash poseidon_commit_spend(Fr::from(self.amount), pubkey_fr, blinding_fr, asset_id_fr) serialized as a 32-byte little-endian Fr element.
// src/privacy/commitment.rs:13-29
pub fn commit(value: u64, randomness: &[u8; 32]) -> Commitment {
    let commitment_bytes = pedersen::commit(value, randomness);
    Commitment::from_bytes(commitment_bytes)
}

pub fn commit_note(note: &ShieldedNote) -> Commitment {
    note.commitment() // Computes Poseidon(amount, pubkey, blinding, asset_id), NOT Pedersen!
}

pub fn verify_opening(commitment: &Commitment, value: u64, randomness: &[u8; 32]) -> bool {
    pedersen::verify(&commitment.0, value, randomness) // Decompresses G1Affine & checks v*G + r*H
}

Impact

Any commitment generated via CommitmentGenerator::commit_note(&note) fails CommitmentGenerator::verify_opening(&commitment, note.amount, &note.randomness) 100% of the time (either failing G1Affine::deserialize_compressed when the 32-byte Poseidon Fr output is not a valid compressed G1 point, or failing point == value * G + randomness * H).

Vulnerability 2: proof_codec Silent Trailing-Byte Acceptance in deserialize_proof / deserialize_vk / bytes_to_field and Endianness Mismatch in field_to_bytes (src/privacy/proof_codec.rs:22–61)

Root Cause

  1. Unchecked Trailing Bytes in deserialize_proof, deserialize_vk, and bytes_to_field (src/privacy/proof_codec.rs:22–26, 37–41, 57–61):
    • Each function wraps bytes: &[u8] in std::io::Cursor::new(bytes) and calls CanonicalDeserialize::deserialize_compressed(&mut cursor) without verifying cursor.position() as usize == bytes.len().
    • As a result, a buffer containing a valid 128-byte compressed Groth16 proof, verifying key, or 32-byte Fr element followed by arbitrary trailing attacker-controlled bytes is silently accepted as valid, breaking strict wire framing and allowing malleable byte representations of the same cryptographic object.
  2. Endianness Contradiction in field_to_bytes (src/privacy/proof_codec.rs:44–54):
    • field_to_bytes(field: &Fr) -> [u8; 32] is documented as /// Convert field element to bytes (32 bytes, big-endian) and right-aligns buf into bytes[32 - len..].
    • However, field.serialize_compressed(&mut buf) in ark-ff always writes 32 little-endian bytes (buf.len() == 32). Thus field_to_bytes(&Fr::from(1u64)) returns [1, 0, 0, ..., 0] (little-endian) instead of big-endian [0, ..., 0, 1] (unlike onchain_verifier::fr_to_be), causing any caller relying on the documented big-endian contract (such as alt_bn128 public-input preparation) to feed byte-reversed field elements.

Vulnerability 3: TransferTx::verify_structure, WithdrawTx::verify, and TrackedTransaction State-Machine Bypass (src/privacy/transaction.rs:200–344)

Root Cause

  1. TransferTx::verify_structure (src/privacy/transaction.rs:201–220):
    • Does not check for duplicate input nullifiers (input_nullifiers[i] == input_nullifiers[j]), all-zero nullifiers ([0u8; 32]), or duplicate output commitments (output_commitments[i] == output_commitments[j]). A TransferTx spending the same Nullifier twice in input_nullifiers returns true from verify_structure().
  2. WithdrawTx::verify (src/privacy/transaction.rs:280–292):
    • Only checks if self.amount < self.fee and if self.to_public.is_empty(). It accepts self.amount == 0 (when self.fee == 0) or self.amount == self.fee (a zero-net-payout withdrawal), accepts invalid Solana recipient lengths (self.to_public.len() != 32, e.g., 1 byte), and accepts an all-zero input_nullifier ([0u8; 32]).
  3. TrackedTransaction::mark_verified & mark_rejected (src/privacy/transaction.rs:335–344):
    • mark_verified(&mut self) unconditionally overwrites TransactionStatus::Rejected { .. } to TransactionStatus::Accepted and performs unchecked self.confirmations += 1 (saturating_add(1) missing).
    • mark_rejected(&mut self, reason) sets self.status = TransactionStatus::Rejected { reason } without resetting self.confirmations = 0, leaving a rejected transaction with non-zero confirmations.

Vulnerability 4: Coordinator HA Failover Permanently Strands In-Flight Mirrored Tasks, Omits Post-Promotion Heartbeats, Suffers Multi-Standby Split-Brain, and Swallows Shard Dispatch Errors (src/coordinator/mod.rs, src/coordinator/role.rs, src/node/mod.rs, src/validator/mod.rs)

Root Cause

  1. Mirrored In-Flight Tasks Permanently Stranded After Standby Promotion (src/coordinator/mod.rs:189–195, 265–288, 365–369, src/validator/mod.rs:69–82):
    • When the primary Coordinator dispatches a shard in submit_task (src/coordinator/mod.rs:365–369), it embeds its own peer ID (coordinator_id: self.network.local_peer_id()) inside Message::TaskRequest and mirrors CoordinatorStateSnapshot (TaskStatus::Assigned) to standbys (mirror_task_state, line 403).
    • Validators executing the shard (Validator::handle_task_request, src/validator/mod.rs:69–82) send Message::ResultRequest exclusively back to that original coordinator_id (the dead primary).
    • When the standby promotes via try_promote_if_stalled (src/coordinator/mod.rs:189–195) or start_stall_watchdog (src/coordinator/mod.rs:265–288), it only flips *role = CoordinatorRole::Primary and never re-dispatches mirrored TaskStatus::Assigned shards under its own local_peer_id(). Consequently, every in-flight task mirrored before failover is permanently stuck (all_chunks_completed never becomes true).
  2. Promoted Standby Never Broadcasts Heartbeats & Multi-Standby Split-Brain (src/node/mod.rs:1911–1938, src/coordinator/mod.rs:240–292, src/coordinator/role.rs:26–27, 69–78):
    • Node::run (src/node/mod.rs:1911–1938) uses a mutually exclusive if ha.primary.is_some() { start_stall_watchdog(...) } else if !ha.standbys.is_empty() { start_heartbeat_broadcast(...) }, and start_stall_watchdog simply breaks on promotion without starting start_heartbeat_broadcast.
    • CoordinatorRole::Standby (src/coordinator/role.rs:26–27) documents primary: PeerId as a tiebreak when multiple standbys consider promoting, but is_stalled (lines 69–78) applies zero rank/tiebreak backoff, so all standbys promote simultaneously at stall_threshold (split-brain).
  3. Coordinator::submit_task Swallows Send Failures/Timeouts and Retains Disconnected Validators (src/coordinator/mod.rs:356–400, src/node/mod.rs:1788):
    • submit_task marks each shard TaskStatus::Assigned (line 360) before calling send_message. If send_message returns Ok(Err(e)) or hits the 1-second tokio::time::timeout (Err(_)), lines 390–399 only log an error without rolling back the shard status or reassigning it, and Node::run's peer-disconnect handler (src/node/mod.rs:1788) never removes disconnected peers from Coordinator.validators.

Proof of Concept (Reproducible Rust Unit Tests)

#[cfg(test)]
mod bounty_poc_tests {
    use crate::privacy::commitment::CommitmentGenerator;
    use crate::privacy::proof_codec::{bytes_to_field, deserialize_proof, field_to_bytes, serialize_proof};
    use crate::privacy::transaction::{TrackedTransaction, TransactionStatus, TransferTx, WithdrawTx, ShieldedTransaction};
    use crate::privacy::types::{Note, Nullifier, ShieldedAddress};
    use ark_bn254::Fr;

    #[test]
    fn poc_1_commit_note_vs_verify_opening_scheme_mismatch() {
        let note = Note::new_native(ShieldedAddress([7u8; 32]), 1_000_000, [42u8; 32]);
        let commitment = CommitmentGenerator::commit_note(&note);
        // CommitmentGenerator::commit_note uses Poseidon, whereas verify_opening uses BN254 Pedersen:
        assert!(
            !CommitmentGenerator::verify_opening(&commitment, note.amount, &note.randomness),
            "CommitmentGenerator::commit_note produces a Poseidon commitment that 100% fails CommitmentGenerator::verify_opening"
        );
    }

    #[test]
    fn poc_2_proof_codec_trailing_bytes_and_endianness() {
        // 1. field_to_bytes claims big-endian in doc comment but outputs little-endian:
        let one = Fr::from(1u64);
        let bytes = field_to_bytes(&one);
        assert_eq!(bytes[0], 1, "field_to_bytes emits little-endian [1, 0, ..] despite big-endian doc");

        // 2. bytes_to_field silently accepts trailing garbage bytes after 32-byte Fr:
        let mut with_trailing = bytes.to_vec();
        with_trailing.extend_from_slice(b"TRAILING_GARBAGE_BYTES");
        assert!(
            bytes_to_field(&with_trailing).is_ok(),
            "bytes_to_field silently accepts trailing unconsumed bytes"
        );
    }

    #[test]
    fn poc_3_transaction_validation_and_state_machine_bypasses() {
        // 1. TransferTx::verify_structure accepts duplicate input nullifiers:
        let dup_nf = Nullifier([9u8; 32]);
        let note = Note::new_native(ShieldedAddress([1u8; 32]), 500, [2u8; 32]);
        let transfer_tx = TransferTx::new(vec![dup_nf.clone(), dup_nf], vec![note], [0u8; 32], 10);
        assert!(transfer_tx.verify_structure(), "TransferTx::verify_structure accepts duplicate nullifiers");

        // 2. WithdrawTx::verify accepts 1-byte recipient, zero net withdrawal, and zero nullifier:
        let withdraw_tx = WithdrawTx::new(Nullifier([0u8; 32]), 10, vec![0xFF], [0u8; 32], 10);
        assert!(withdraw_tx.verify(), "WithdrawTx::verify accepts 1-byte recipient and 0 net payout");

        // 3. TrackedTransaction::mark_rejected leaves confirmations > 0 and mark_verified resurrects Rejected:
        let mut tracked = TrackedTransaction::new(ShieldedTransaction::Withdraw(withdraw_tx));
        tracked.mark_verified();
        tracked.mark_rejected("invalid proof".to_string());
        assert_eq!(tracked.confirmations, 1, "Rejected transaction still reports confirmations == 1");
        tracked.mark_verified();
        assert_eq!(tracked.status, TransactionStatus::Accepted, "Rejected transaction resurrected to Accepted");
    }
}

Recommended Fix

  1. src/privacy/commitment.rs: Align CommitmentGenerator on a single commitment scheme (or provide explicit verify_note_opening(commitment: &Commitment, note: &ShieldedNote) -> bool that checks *commitment == note.commitment(), and document commit / verify_opening as Pedersen-specific).
  2. src/privacy/proof_codec.rs: In deserialize_proof, deserialize_vk, and bytes_to_field, check if cursor.position() as usize != bytes.len() { return Err(...); } to reject trailing bytes; in field_to_bytes, either serialize big-endian via field.into_bigint().to_bytes_be() or update the implementation/documentation to match little-endian to_bytes_le().
  3. src/privacy/transaction.rs: Reject duplicate/zero input_nullifiers and duplicate output_commitments in TransferTx::verify_structure; require self.to_public.len() == 32, self.amount > self.fee, and self.input_nullifier.0 != [0u8; 32] in WithdrawTx::verify; guard TrackedTransaction::mark_verified against TransactionStatus::Rejected and reset self.confirmations = 0 in mark_rejected.
  4. src/coordinator/mod.rs, src/coordinator/role.rs, src/node/mod.rs: On standby promotion, re-dispatch all mirrored TaskStatus::Assigned shards with coordinator_id = self.network.local_peer_id(), spawn start_heartbeat_broadcast, add deterministic standby rank backoff to is_stalled, roll back/reassign shards when send_message fails or times out in submit_task, and prune disconnected peers from Coordinator.validators.
