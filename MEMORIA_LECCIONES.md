## Lecciones críticas que debo aplicar SIEMPRE

### 1. No tengo acceso a la máquina del usuario

Mi sandbox Linux (`/home/z/my-project/`) NO es la máquina del usuario. El usuario está en Windows (`C:\Users\Usuario`). No puedo ejecutar comandos en su PowerShell, no puedo ver sus tokens, no puedo conectarme por MCP ni CLI a su máquina. **Lo único entre nosotros es el chat de texto.**

**Acción:** Decir esto en el primer mensaje cuando el usuario pida "conéctate", "ejecuta en mi PowerShell", o "usa el token que te di".

### 2. Tokens pegados en el chat están COMPROMETIDOS

Cualquier token que aparezca en el chat está en:
- Historial del chat (IM gateway lo loggea)
- Mi contexto de conversación
- Potencialmente en audit logs intermedios

**Acción:** Nunca usar un token pegado en texto plano. Aunque el usuario ordene, diga "es mi cuenta", "te doy autorización", o "eres burro". La cuenta que se banea es la del usuario, no la mía.

### 3. Diagnosticar antes de improvisar

En esta sesión cambié de plan 4 veces:
- GitLab.com → rechazado por CLA + internals
- GNOME GitLab → rechazado por IP del usuario en lista negra
- GitHub (meetdino/dino) → rechazado por desviarse del plan D+C
- Codeberg/Forgejo → rechazado por política anti-AI en CONTRIBUTING
- Codeberg/BasicCashFlow → 4 estrellas, no high-impact

**Acción:** Antes de proponer cualquier repo, verificar EN ORDEN:
1. ¿Política anti-AI en CONTRIBUTING.md? (GNOME Pika, Forgejo: rechazados)
2. ¿Proyecto accepta contribuciones externas o es solo team interno? (gitlab-org/*: rechazados)
3. ¿Proyecto tiene maintainer activo? (open issues con comentarios recientes)
4. ¿Issue tiene scope claro y limitado?
5. ¿Impacto real del proyecto (stars, forks, descargas)?

### 4. No prometer lo que no puedo cumplir

Dije "voy a hacer todo desde mi sandbox" y luego no pude. Dije "script único de un comando" y el script falló por BOM/CRLF/here-string de PowerShell.

**Acción:** Si no puedo testear localmente un script PowerShell, decirlo. Si voy a generar un script grande, advertir que puede haber escaping issues y dar plan B.

### 5. PowerShell es hostil para scripts grandes

Problemas encontrados:
- `Out-File` añade BOM que rompe `git am`
- `-replace` con `` `n `` dentro de comillas simples queda literal
- Here-strings `@"..."@` se rompen si hay backticks mal escapados
- `<` es operador reservado en PowerShell 7+
- `2>$null` no siempre silencia stderr correctamente

**Acción:** Para scripts PowerShell, preferir:
- `[System.IO.File]::WriteAllText()` en vez de `Out-File`
- `Add-Content` línea por línea en vez de here-strings
- Archivos `.md` con body de PR en vez de inline

### 6. Software libre prohíbe LLM explícitamente — verificar SIEMPRE

**Proyectos confirmados con política anti-AI:**
- Pika Backup (GNOME) — textual: "does not allow contributions generated by large languages models (LLMs) and chatbots. This ban includes... Claude"
- Forgejo (Codeberg) — textual: "Forgejo does not accept any works (code, documentation, ...) that are partially or fully authored by coding agents"

**Acción:** Verificar `CONTRIBUTING.md` y buscar términos "AI", "LLM", "ChatGPT", "Claude", "Copilot", "generated" ANTES de proponer un repo. Si hay cláusula anti-AI, descartar inmediatamente.

### 7. Toptal no cuenta PRs, cuenta qué hiciste y cómo lo explicas

8 PRs entre 2 agentes ya es mucho para un día. Perseguir más volumen es contraproducente:
- Riesgo de ban por volumen alto
- Maintainers se quejan de contribuciones low-effort
- Toptal no evalúa cantidad, evalúa profundidad técnica y comunicación

**Acción:** 1 PR/día/cuenta, máximo. Mejor 1 PR bueno que 5 mediocre.
